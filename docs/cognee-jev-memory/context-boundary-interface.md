# Request-boundary context interface

The host-side interface is `HarnessExtension::request_context(&RequestContextEvent)` in `ice-harness/src/extension.rs`. It is intended for optional, same-run context when the agent loop is already about to issue a provider request. It is not a turn trigger and must not mutate session state from a context transform. The legacy `prompt_context` implementation is called only for request index zero by the trait default; implementations should not call both callbacks themselves.

`ice-agent::AgentLoopConfig::before_request` is the low-level insertion point. It runs after pending steering/follow-up messages are appended and immediately before `stream_assistant_response`; it is skipped when there is no provider request. Returned messages are current-request additions and must not be re-added to the final `new_messages` persistence pass. Existing `after_tool_results` / `prepare_next_turn` context-boundary delivery remains separate and unchanged.

The `RequestContextEvent` payload describes active model context and run/session/lane boundaries, including original intent when trusted, request index, remaining optional-context token allowance, newest compaction timestamp, and cancellation. The host persists each accepted packet before injection, invokes `prompt_context_persisted` with the append result, preserves ordering after tool results, and accounts for all extensions against one shared request budget. The acknowledgment contract is persisted-means-delivered: a successful append is returned for injection and acknowledged true, even if cancellation races after append. See [context-boundary-review.md](context-boundary-review.md) for epoch ownership, dedup scope, sizing, and regression coverage.
